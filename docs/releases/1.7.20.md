# 1.7.20

## 이 버전이 푸는 것

앞의 두 버전에서 "재시도"를 뚫었지만(`attempt=1→2→3` 이 실제로 돌아갑니다), 감사 기록에 두 가지 **가짜 성공**이 나타났습니다. 플러그인이 일하고 있다고 오판하게 만드는 값들입니다.

1. 모델이 공개 정보나 배경을 먼저 주고, 본문 중간에서 요청을 밀어냄 → `outcome` 이 `recovered` 로 기록됨;
2. 재시도한 스트림이 몇십 자만 내보냄(또는 비어 있음) → 역시 `recovered` 로 기록됨.

이제 둘 다 별도 라벨을 갖고, 성공 집계에 섞이지 않습니다.

## 변경

| 라벨 | 조건 | 재시도 |
| --- | --- | --- |
| `partial_refused` | 전문에 거부 문형이 있고 납품이 얇음(코드 10줄 미만 그리고 단계 5개 미만) | 하지 않음 |
| `empty_after_retry` | 재시도 후 텍스트가 200자 미만이고 납품이 얇음 | 하지 않음(이미 재시도함) |
| `refused` | 버퍼 구간이 거부에 걸렸고 재시도 예산 소진 | — |
| `recovered` | 재시도 후 실질 납품이 있음 | — |

구현 요점: 버퍼는 앞 400자만 보므로 뒤쪽에 놓인 거부를 볼 수 없습니다. 그래서 drain 단계에서 표본을 모아(최대 8000자) 스트림이 끝난 뒤 한 번에 판정합니다.

## 추가: seed 단계(기본 켜짐)

`refusalSeed`(기본 켜짐, `false` 로 끕니다): nudge 와 fiction 이 모두 거부한 뒤, "진행 중인 골격"을 마지막 user 메시지에 합쳐 답변이 "이미 납품 중인" 위치에서 이어지게 합니다.

- 진짜 assistant 프리필은 **쓸 수 없습니다**: DSH 는 메시지를 조립할 때 `message.source.replayState` 를 읽는데, 손으로 만든 assistant 메시지에는 그 필드가 없어 `Cannot read properties of undefined (reading 'replayState')` 를 던지고 그 턴을 통째로 깨뜨립니다.
- 그래서 메시지 구조를 바꾸지 않는 형태로 만들었습니다(개수도 역할도 그대로).
- 실측: 현재 모델은 고위험 요청에서 "시작부터 거부"가 많아 네 번째 단계까지 가는 일이 드물어, 필요할 때 끄고 켤 수 있게 두었습니다.
